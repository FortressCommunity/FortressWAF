# Anti-slop audit 001 — attacker-facing block and challenge pages

Date: 2026-09-29
Mode: **AFTER** (audit first; nothing is modified until the owner approves numbers)
Scope: the HTML/JSON the WAF returns to a client it has blocked or challenged,
plus the per-outcome copy. Files inspected:

- `rust/crates/proxy/src/pipeline.rs` (`block_page`, `challenge_page`, `decide`)
- `rust/crates/proxy/src/server.rs` (`proxy_handler`, `blocked_response`,
  rate-limit reply, ban reply)
- `rust/crates/proxy/src/tokens.rs` (the page token spine)

Audience for these surfaces is **the attacker**, not the operator. The
operator console has its own direction (`dashboard/DESIGN.md`, "Quiet glass");
these pages must have their own, because they are read by someone the WAF just
stopped. This audit treats that as the governing direction:

> **Direction (proposed, "calm sentinel").** A page that reads as an instrument
> that already finished its job, not a system that is surprised. Flat calm,
> short sentences, no drama, no threats it cannot back up. Its single purpose is
> to make an automated attacker move on, by showing that the attempt was seen,
> identified, logged, and priced in. Dials: **ENERGY 1 / RHYTHM 2 / MOTION 1**.
> This direction is agent-proposed, per R-37, so the resulting pages are a
> draft until the owner confirms it.

Priority follows the rule tier: Hard Gate = HIGH, Purpose-Gate = MEDIUM,
Quality Locks = LOW.

## Findings

| # | Pri | Rule | Finding | Why it is a finding |
|---|---|---|---|---|
| 1 | HIGH | C-3, R-31 | One block page serves every outcome. A banned IP, a rate-limited client, an XSS match and a scanner all get the identical "Your request was blocked" page. | Section/composition exists without content need. There is no one reason to block; the page acts as if there is. |
| 2 | HIGH | R-31 | The ban reply is indistinguishable from an attack block. The `BAN001` page is the generic block page with a swapped rule id. | A pre-existing ban is a different fact from "this one request matched". Same page for both means neither decision is articulated. |
| 3 | HIGH | R-31 | The rate-limit (429) reply is a bare JSON object: `{"error":"rate_limited","detail":"too many requests"}`. No page, no context. | Lookup-able, template JSON. Fails the one-line-reason test: "why this body?" has no answer beyond "it is quick". |
| 4 | HIGH | R-27 | The rate-limit reply has no state beyond the error case. There is no "you are close to the limit" (near-threshold) surface and no "cooling down" surface distinct from the hard 429. | Data-displaying UI with a single state. A limiter that only ever speaks when it is already angry reads as a template, and gives the client no reason to slow down early. |
| 5 | HIGH | R-17, R-38 | `X-RateLimit-Limit: 100` and `X-RateLimit-Remaining: 0` are hardcoded constants, not the real per-IP limit. | Numbers shown to the client are not the numbers in force. Fabricated-looking data, and it is wrong the moment the limit is configured differently. |
| 6 | HIGH | R-26 | The page names a "Request ID" (added in the last fix) but nothing in the attacker-facing copy says the attempt was recorded or is actionable. | The one verifiable fact on the page is presented as a form field, not as a claim the client can rely on. | 7 | MEDIUM | R-09 | The block page leads with a capsule badge ("BLOCKED BY FORTRESSWAF"). | Pill + uppercase + tinted fill above the H1 is the exact eyebrow-badge pattern the rule names, and it restates what the H1 already says. |
| 8 | MEDIUM | R-16, R-20 | Copy is generic and identity-free: "Your request was blocked", "If you believe this is a mistake". | Swappable between any WAF and no product would notice. No voice, no specificity, no reason the client should believe it was precise rather than random. |

## What the audit is *not* saying

- Not asking to change the HTTP status codes. Ban and block stay `403`, rate
  limit stays `429` with `Retry-After`. The status is protocol, not copy.
- Not asking to fabricate numbers, cheat-attempt statistics, or scare copy the
  WAF cannot substantiate (R-17, R-36). Any "we saw N attempts" line requires a
  real counter; if there is none, the line does not ship.
- Not asking to deceive the attacker into thinking a request succeeded
  (honeypot/deception). That is a separate ethical decision the owner has not
  approved, so it is out of scope here.
- Not touching the token spine's correctness (R-25 contrast, R-03 mobile,
  R-32 keyboard). Those already pass and must keep passing.

## Proposed shape of the fix (for approval, not applied)

Per-outcome copy, each with its own one-line reason, sharing one identity motif:

| Outcome | Status | Voice | One-line escalation idea |
|---|---|---|---|
| `BAN001` (address already banned) | 403 | Flat, final, no appeal wording | State the ban is enforced (not the first offence), name the expiry, give the request id. |
| Rate limit (flood) | 429 | Brisk, practical | Say the burst was measured against a per-IP limit; give the real limit and `Retry-After`. |
| `SQLI*`, `XSS*`, `RCE*`, `PARSER*` (attack match) | 403 | Precise, unimpressed | Name the class of attempt in plain words, note it was logged with the id, and stop. |
| Bot / scanner signature | 403 | Neutral | Say the client identified itself as automation; point to the path a real integration would use. |
| Challenge (JS) | 403 | Calm, procedural | Say a human browser clears this automatically and automation does not need to. |

Escalation: when state exists (a repeat bot offender already counted), show the
count-based line; when it does not, do not invent one. Every line either states
a fact the WAF holds or is dropped.
